# 文稿自动保存协议

## 三种状态

1. **本地保存**：操作已进入本机持久化队列，但没有服务器收讫证明。标签页关闭/离线/超时时仍必须可见。
2. **服务器已接收**：操作以 `(doc_id, device_id, device_seq)` 幂等身份写入 PG `doc_operations`，响应包含收讫版本。
3. **命名保存点**：在服务器当前版本提交快照和名称，写入 `doc_checkpoints`；本地“想建保存点”不是第三种最终状态。

## 操作模型

```json
{
  "id": "dev-a:17",
  "deviceId": "dev-a",
  "seq": 17,
  "type": "update_node",
  "nodeId": "seed-1-...",
  "parentId": "root",
  "afterNodeId": null,
  "beforeNodeId": null,
  "content": "新内容",
  "range": { "start": 12, "end": 18, "line": 2 }
}
```

身份只由 `(deviceId, seq)` 决定；重试时身份不变。服务器对已存在身份比较规范化操作指纹：

- 指纹相同：幂等成功，不重复应用；
- 指纹不同：返回 `409 OP_IDENTITY_CONFLICT`，不得覆盖、删除或按时间戳选版本；
- 身份不存在：在条件版本事务中应用。

## `POST /api/docs/:id/operations`

请求：

```json
{
  "expectedVersion": 41,
  "clientSubmitId": "dev-a-172...",
  "operations": []
}
```

响应：

- `200`：`serverVersion` 与每个操作的收讫版本；
- `412 STALE_BASELINE`：版本条件不满足，返回服务器版本；客户端拉取云端新稿后做共同祖先三方合并；
- `409 OP_IDENTITY_CONFLICT`：同编号不同指纹；
- `0/504/断连`：结果未知，不是失败结论。队列保持原身份，不重建整稿，下次先探测或直接幂等重放。

## 恢复

恢复视图必须并列展示：

- 共同祖先；
- 当前设备分支；
- 云端新稿。

合并依据节点是否相对共同祖先新增、删除、移动或修改，而不是比较 `updatedAt`。纯不同位置编辑可自动变基；以下情况进入人工处理：

- 本地改、云端删；
- 本地删、云端改；
- 插入锚点缺失或同级顺序冲突；
- 同一节点双方改成不同内容。

人工处理产生新的变基操作，并用 `supersedes` 指向旧操作；恢复动作自身保存审计，可生成反向操作撤销。

## 存储配额

本地写队列失败时：

1. 清理预览、派生索引、云端快照等可重建缓存；
2. 重试写入唯一未上传操作；
3. 仍失败则阻止宣称“已保存”，并在编辑器准确标出未可靠保存的行范围；
4. 任何情况下不得删除唯一未上传编辑。

## 验收场景

- 离线编辑后关闭重开：恢复队列和未确认行范围；
- 提交成功但回执丢失：重放得到幂等确认；
- 两个标签页：共享 `localStorage` 队列，通过 Web Locks 串行化本地修改与同步，BroadcastChannel 刷新视图；
- v1 整稿格式升级：转换为 v2 节点操作再走分支合并；
- 云端版本前进：过期基线提交收到 412，展示三方恢复；
- 同编号不同内容：收到 409 并人工处理。

## 文档级乐观锁与节点操作合并的取舍

- **文档级乐观锁**：实现简单，请求携带整篇文档和 `expectedVersion`。任何并发编辑都会让后提交者收到 412；即使双方改的是不同段落也只能整篇三方 diff，恢复粒度粗，容易诱发“下载云端稿—覆盖本地稿”的错误。
- **本方案节点操作合并**：版本条件仍在服务器事务中严格检查，但冲突检测落在节点身份和操作图上。不同节点的插入、删除、修改可以自动变基；只有同节点双方改内容、改/删冲突、锚点缺失或顺序冲突才要求人工处理。
- 因此版本号用于防止陈旧基线，节点图用于判断能否自动合并；不能用时间戳替代二者。
